# 技術方針 — おでかけペット

## 基本原則

**「動くものをシンプルに」**。VM のメモリ制約（MemAvailable 約0.3〜0.4GiB）下でも開発・実行が成立し、ビルド工程なしに静的ファイルとして配信できる構成を採る。複雑さは体験ではなく実装で増やさない。

## アーキテクチャ制約（変更不可）

以下は企画レベルで確定した制約である。Kiroが代替案を提案した場合もこれに従い、変更するには明示的な上位承認が必要。

### ビルド工程なしの静的Webアプリ
- HTML / CSS / JavaScript（ES Modules）のみで構成する
- npm / webpack / Vite 等のビルドツールは使用しない
- `<script type="module">` でモジュールを読み込む構成とする
- ブラウザで直接開けば動作し、静的ホスティングに zip をアップするだけで公開できる形を維持する

### バックエンドサーバーなし
- サーバーサイド処理（Node.js、Python等のAPIサーバー）は持たない
- データベースサーバー（MySQL、PostgreSQL等）は持たない
- 全ての処理はブラウザ上のJavaScriptで完結する

### データ保存は localStorage
- ペットの状態、アルバム、訪問履歴はすべて `localStorage` に保存する
- キーの命名規則は `odekakepet::{entity}::{id}` 形式とする（例: `odekakepet::pet::current`）
- `localStorage` の容量制限（通常5MB）を意識した設計にする。画像データをそのまま保存しない
- IndexedDB は MVP では使用しない（シンプルさを優先）

### おでかけの受け渡しは「おでかけコード」方式
- 友達の場所へのおでかけは常時稼働サーバーを必要としない方式で実現する
- **おでかけコード**: 訪問リクエスト／訪問結果を Base64 エンコードした文字列として受け渡す
  - 訪問リクエスト: ホーム情報（ペット名・種類・性格パラメータ）を含む文字列を発行→友達が入力
  - 訪問結果: 発生したイベント・おみやげを含む文字列を帰宅時に読み込む
- コードのフォーマットは `バージョンプレフィクス:Base64ペイロード` とし、バージョンは変更追跡のために必須
- コードの最大長はQRコードや手入力を考慮し、合理的な範囲に収める（概ね500文字以内を目安とする）

### Instagram連携APIは使わない
- Instagram Graph API 等の外部APIは使用しない
- 共有は「ユーザーが絵日記カードをPNG画像として端末に保存し、自分の操作で投稿する」方法のみ
- アプリからの自動投稿・シェアシート呼び出しは行わない

## 技術スタック

| 区分 | 採用技術 | 理由 |
|---|---|---|
| マークアップ | HTML5 | ビルド不要、静的配信可能 |
| スタイリング | CSS（カスタムプロパティ活用） | ビルド不要、変数でテーマ管理 |
| スクリプト | JavaScript ES2022（ES Modules） | ビルド不要、モジュール分割可能 |
| データ保存 | localStorage | サーバー不要、ブラウザ標準 |
| 画像生成 | Canvas API | ブラウザ標準、PNG書き出し可能 |
| フォント | システムフォント or ウェブフォント（Google Fonts CDN） | ビルド不要 |

## モジュール設計方針

- 1ファイル1責務。ファイル名はケバブケース（`pet-state.js`、`event-generator.js`）
- グローバル変数は使用しない。モジュール間はexport/importで疎結合に保つ
- 状態管理は中央の `store.js` に集約し、各モジュールが直接 `localStorage` を読み書きしない
- イベントハンドラの登録はHTMLのインラインonclick属性ではなく、`addEventListener` で行う

## 状態遷移の記述規約

状態は必ず文字列リテラルとして定数化し、コード中に生の文字列を書かない。

```javascript
// 正: 定数を使う
const PET_STATE = {
  HOME: 'home',
  VISITING: 'visiting',
  RETURNING: 'returning',
};

// 誤: 生の文字列を条件分岐に使う
if (pet.state === 'at_home') { ... }
```

ペットの状態遷移は以下の単方向ループのみ許容し、例外状態を持たない:

```
home → visiting → returning → home
```

状態を `visiting` から `home` に直接変更する処理は書かない。必ず `returning` を経由する。

## 絵日記カード生成

- Canvas 2D API で描画し、`canvas.toBlob()` → `<a download>` でPNGとして保存する
- 比率: 9:16（1080×1920px 相当の論理サイズ）
- 構成要素: 訪問先の背景イラスト、ペット名、イベント要約文（最大100文字）、日付、サイトのロゴ
- フォントサイズは `rem` で指定し、高解像度デバイスでの書き出しに対応する

## テスト方針

- 状態遷移とイベント分岐は単体テストで固定する（ブラウザ外で実行できる純粋関数として設計する）
- テストフレームワークはビルド不要で使える `<script type="module">` 上で動く軽量なものを採用する
- おでかけコードの往復テスト: エンコード→デコードでデータが欠けないことを単体テストで保証する
- カード生成のスナップショット確認: 代表ケースのPNG出力を目視確認する（自動diff は MVP では行わない）

## セキュリティ・プライバシー

- `localStorage` に保存するデータにユーザーの個人情報は含めない（ペット名はユーザーが自由入力するため、入力値のサニタイズを行う）
- おでかけコードをURL経由で渡す場合、コード文字列をそのままURLパラメータに含めてよい（個人情報を含まない設計とする）
- `innerHTML` への直接代入は行わない。DOMの生成は `textContent` / `createElement` を使う（XSS対策）

## 開発環境

- エディタ: Kiro CLI（本プロジェクトはKiroを主開発ツールとする）
- ブラウザ: Chrome / Firefox の最新版での動作確認を基準とする
- ローカル実行: `python3 -m http.server` 等の簡易HTTPサーバーで静的ファイルを配信する（`file://` 直接開きはES Modulesで動作しないため使わない）
- デプロイ: 静的ホスティング（具体的なホスティング先は承認後に確定）

## 将来の拡張に関する注記

以下はMVP後の再評価事項であり、現在の設計では考慮しない:
- IndexedDB への移行（容量が実際に問題になった場合）
- サーバー方式への移行（常時稼働サーバーの費用・運用が承認された場合）
- 複数デバイス間の同期（おでかけコード方式の延長として再設計する）
