# 企画再評価と最小修正計画 — おでかけペット

作成: 2026-11-26（総一郎さんの再評価指示に基づく）。
新コンセプト: **「あなたの日常や記憶から、自分だけの世界を形成していくペット」**

## 1. 批判の整理

現状の説明では「旅かえるにAI日記を足しただけ」に見える、という指摘は正しい。
当時の実装では:

- 性格（curiosity / sociability）は生まれつき固定で、出来事の条件分岐にしか
  使われていなかった（育たない、変わらない）
- 冒険履歴はアルバムに並ぶだけで、次の冒険に何も影響しなかった
- AIは日記の文章生成だけに使われ、世界観や個性の形成には関与していなかった
- 端末内／クラウドの分担は「日記をどちらで書くか」だけの話で、
  個人的な情報の扱いという設計になっていなかった

## 3. 既存サービスとの差別化

| 観点 | 旅かえる | 従来のおでかけペット | 再評価後 |
| --- | --- | --- | --- |
| 旅の主体 | かえるが勝手に旅する（眺める） | 行き先を選んで送り出す | 同左＋記憶が次の旅を変える |
| 記録 | 写真・おみやげが届く | アルバムに残る | 記録が「記憶」として蓄積し、性格・出来事・行き先の見え方に還流する |
| 個体差 | ほぼ無い | 生まれつきの性格のみ | 経験で性格が育つため、履歴ごとに個体が分岐する |
| AI | なし | 日記の文章生成のみ | 記憶の文脈を持つ日記生成＋端末内／クラウドの許可設計。性格形成と記憶の集計は端末内の決定的処理 |
| 他者との接続 | なし | コードで友達の家を訪問 | 同左（ブログペットの「訪問」文化の復活） |
| プライバシー | — | 特に設計なし | おもいでは端末内が既定。クラウドへ出す範囲は利用者が選ぶ |

差別化の核は「眺める旅」ではなく「一緒に積み重なる記憶」であり、
AIは文章の飾りではなく、記憶を個性と物語に変えるために置く。

## 4. 最小修正計画（実施済み）

### 4.1 記憶の蓄積と影響（新規: src/domain/memory.js）

- 冒険履歴（完了済み Visit）から記憶を導出する: 総回数、行き先ごとの
  回数、お気に入りの場所、おみやげ数、場所ごとの前回の出来事
- 経験と性格の形成: 旅ごとに経験値（XP）が貯まる。出来事の条件が
  鍛えた軸に多く入り、おみやげは好奇心に効く。XP がしきい値（3 / 8）を
  超えると実効性格が段階的に上がり（上限2）、出来事の条件判定は
  実効性格で行う。つまり「育った性格が、次に起きる出来事を変える」
- 反復回避: 同じ場所で前回と同じ出来事は、候補が複数あれば外す
- 行き先への影響: おでかけ選択画面に記憶バッジ（はじめて／○回／
  お気に入り）と、記憶に基づくおすすめ文（未訪問の場所への興味、
  または お気に入り）を出す

### 4.2 端末内／クラウドの分担と理由

分担の原則は「個人的な文脈は端末内、表現の生成はハイブリッド」:

- 記憶の集計・性格の形成: 端末内の決定的な処理（AI でもクラウドでも
  ない）。個人的な履歴そのものは端末の外に出ない
- 記憶の要約（digest）: 端末内で組み立てる短い文脈。これをクラウド
  生成に渡すかどうかは、ホーム画面の設定
  「おもいでをクラウドの日記にも使う」（既定オフ）で利用者が決める
- 日記の生成（diary-ai の planDiaryAttempts）:
  - 許可なし: まず端末内のみ（mode: 'on_device'）で記憶入りの生成を
    試みる。成功すれば記憶は端末の外に出ていない。失敗したら、
    記憶を除いたプロンプトで通常のハイブリッド生成に進む
  - 許可あり: 記憶入りのまま通常のハイブリッド生成
- 理由: 記憶は「その人とペットの履歴」という最も個人的な情報。
  端末内で処理できるものは端末内で完結させ、クラウドの表現力は
  「今日の出来事」という非個人的な素材に使うのが既定。許可した
  利用者だけが、記憶の文脈ごとクラウドの表現力を得る

### 4.3 UIでの見せ方

- ホーム画面「せいかく」パネル: 実効性格の言葉、軸ごとの成長ドットと
  次の成長までの残り、おもいでの要約（件数・おみやげ数・お気に入り）
- ホーム画面「AIとプライバシー」パネル: 上記の許可トグルと説明文
- おでかけ画面: 行き先カードの記憶バッジとおすすめ文
- 日記カード: 推論元バッジ（既存）。記憶入りの日記は本文に過去への
  言及として現れる

### 4.4 大会別の訴求

- Kiroween（Resurrection）: ブログペットの「不在の楽しみ」と
  「友達のページへの訪問」の復活を前面に。記憶の形成は、ブログ
  ペットが持たなかった「続いていく関係」として位置づける。
  Kiro のスペック駆動開発（.kiro/specs、フック、性質テスト）は従来
  どおり中核の訴求
- BuildHybridAI: ハイブリッドの必然性を「プライバシーと到達範囲」の
  両面で示す。記憶という個人的文脈は端末内が既定、クラウドは許可制。
  機能ごとに推論モードを分ける設計（記憶入り=端末内のみ試行、
  通常=端末内優先ハイブリッド）は、公式 FAQ が認める
  「機能ごとに推論モードを分ける」形そのもの

## 5. 行き先の改名

- 「星屑工房」は使わない（総一郎さんの決定）。新しい名前は
  **「月夜の小屋」**。選定理由: 他の行き先（森の標本室・時計塔キッチン）
  と同じく「場所そのもの」を指す名前にし、星のかけらとランプという
  既存の出来事の内容に合う語を選んだ。「工房」という作り手の枠と
  「星屑」という旧企画由来の語は外した
- スポットID（hoshikuzu-kobo）は保存データ互換のため変更しない
- 出来事文中の「工房」は「小屋」に、「星屑のランプ」は
  「星あかりのランプ」にそろえた。住人のルミの名前は変えない

## 6. リスクと残件

- **BuildHybridAI の英語対応**: 提出物は英語必須で、アプリも最低限の
  英語対応が求められる。現状のアプリ UI は日本語のみ。今回は提出文と
  動画（英語ナレーション）で補う計画だが、Design /
  Technological Implementation の減点要因になりうる。締切
  （12/1 07:00）までの残り時間では、UI の二言語化は行わない判断
- **App Check デバッグトークン**: FAQ はデバッグトークンを公開
  リポジトリにコミットしないよう案内する一方、審査員が公開URLから
  実行する構成ではトークンの埋め込みが前提になる。現行はコンソールで
  登録済み・いつでも失効可能なトークンをコードに置く運用
  （2026-11-24 の判断）。提出文では App Check の構成を明記する
- **オンデバイス生成の実機確認**: 端末内のみ（on_device）の試行は、
  Gemini Nano を持つ実機 Chrome でしか成功を確認できない。
  クラウドブラウザでは失敗して次の試行に進む経路のみ確認可能。
  提出前に総一郎さんの Pixel（Chrome）での確認が望ましい
- **Kiroween の既存動画**: 撮影済み動画の画面には旧名「星屑工房」が
  写っている。内容面では今も使えるが、改名を徹底するなら
  おでかけ画面のカットだけ撮り直しが要る（締切 12/5、余裕あり）
